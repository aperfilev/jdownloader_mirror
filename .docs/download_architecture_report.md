# JDownloader Download Architecture Investigation

**Date:** 2026-11-11  
**Project:** jdownloader_mirror / svn_trunk

## 1. Overview

JDownloader uses a layered download model:

* `DownloadLink` – the logical link object, holds metadata, properties, mirror ID, chunks, hash info.
* `Downloadable` – runtime view of a link, provides `getChunksProgress()`, `getFileOutputPart()`, etc.
* `DownloadInterface` implementations – `HTTPDownloader`, `OldRAFDownload`, `SegmentDownloader`, `SimpleFTPDownloadInterface`, etc. They perform the actual byte transfer.
* `DownloadWatchDog` / `SingleDownloadController` – scheduler that picks candidates, handles retries, mirror handling.

## 2. Resume / Completion Map Files

### Part file
* Active download is written to `<target>.part` in the download folder.
* On finalization the part file is renamed to the final filename.

### Bytes map / resume metadata
* Resume state is stored in a side-car file next to the part file.
* File name is generated by `BytesMappedFileManager.getFileBytesMapID(File)`:
  ```
  <len>-<MD5(filename)>.<ext>.jdresume
  ```
  Example: `24-5d41402abc4b2a76b9719d911017c592.txt.jdresume`
* The file lives in the same directory as the part file.
* Content is a JSON serialized `BytesMappedFileStorable` which contains:
  * `name` – file name
  * `fileBytesMap` – view of marked / loaded byte ranges
  * `finalSize`, `markedBytes`, etc.

`BytesMappedFileManager` handles:
* `readFileBytesMap(File)` – loads the `.jdresume` if present
* `write(BytesMappedFile)` – persists the map on flush / completion
* Locking via `BytesMappedFileManager` singleton to avoid concurrent writes.

### Chunking
* Downloads can be split into multiple chunks per file.
* `DownloadLink` property `PROPERTY_CHUNKS = "CHUNKS"` stores the configured chunk count.
* `DownloadInterface` implementations use `HTTPChunk` / `RAFChunk` objects.
* Chunk progress is stored in `long[] chunksProgress` on the link and persisted via the bytes map.
* `HTTPDownloader` uses `BytesMappedFile` to track which byte ranges are already downloaded, enabling resume per chunk and per mirror.

## 3. Mirrors

### Mirror identification
* `DownloadLink` has property `PROPERTY_MIRRORID = "MID"`.
* Host plugins can override `PluginForHost.getMirrorID(DownloadLink)` to return a stable identifier for the same file served from different hosts / mirrors.
* Mirror detection also uses file name, file size and hash info. `MirrorPackage` aggregates links:

```java
MirrorPackage mirrorPackage = mirrorPackages.get(mirrorID);
...
mirrorPackage.add(link);
```

`MirrorPackage.add()` checks size mismatch and hash mismatch and updates:
* `bytesLoaded` – max of part file length or view bytes loaded
* `bytesTotal` – max of reported sizes
* `online/offline` status
* `enabled` flag

### Mirror handling behavior
* `DownloadLinkAggregator implements MirrorPackageSetup` groups links by mirror ID.
* When a link is actively downloading, other mirrors of the same file are put into a conditional skip state via `MirrorLoading`.
* `MirrorLoading implements ConditionalSkipReason, DownloadLinkCondition`:
  * `finalize(DownloadLink link)` – when the dependency link finishes, the waiting mirror link is marked `FINISHED_MIRROR` and its metadata is copied.
  * `isConditionReached()` – true when the dependency link has no controller → the mirror can be retried.
* Effect: **mirrors are not run in parallel**. Only one mirror per file is active at a time. The others are skipped with a conditional skip reason and automatically unblocked when the active mirror finishes or is removed.

### Mirror replacement / stale mirrors
* The `MirrorLoading` condition is cleared when the dependency link finishes or is removed, so the mirror becomes eligible again.
* If the active mirror fails / is removed, the conditional skip is released and the next candidate can be tried.
* Mirror selection is performed by `DownloadLinkCandidateSelector` which evaluates candidates per link, respects account / proxy limits, and picks the best candidate.
* No built-in “simultaneous multi-mirror” download is present. The architecture is single-active-mirror per file with fallback.

## 4. Download completion / state persistence

* Download state is persisted in:
  * The `.part` file on disk
  * The `.jdresume` side-car for byte-range map
  * `DownloadLink` properties are stored in JDownloader’s internal database / JSON storables
* `DownloadLinkView` provides `getBytesLoaded()`, `getBytesTotal()`, `getChunksProgress()`.
* `FileBytesMap` tracks which ranges are marked as downloaded. The map is flushed via `BytesMappedFileManager.write()`.

## 5. Implications for requested features

### Verify data integrity for archives, erase only corrupted blocks
* The current bytes map tracks *which* byte ranges have been downloaded, not their integrity.
* Hash verification is done at file level via `HashInfo` / `HashCheckPluginProgress` after download completes.
* To support per-block integrity and re-download of only corrupted blocks:
  * Extend `FileBytesMap` to store per-range hash / checksum.
  * On archive verification failure, map corrupted ranges back to byte offsets and mark those ranges as “needs re-download” in the bytes map.
  * The existing chunk / resume infrastructure can re-request only the missing ranges via HTTP Range requests.

### Simultaneous downloads from multiple mirrors or replace stale mirrors without losing progress
* Current design enforces single active mirror per file via `MirrorLoading`.
* To allow multi-mirror parallel download:
  * Remove or make optional the `MirrorLoading` conditional skip.
  * Allow `MirrorPackage` to aggregate progress from multiple mirrors into a single `BytesMappedFile`. The bytes map already supports multiple sources writing to the same file via `BytesMappedFileManager.lock()`.
  * Candidate selection would need to allow multiple candidates for the same `MirrorPackage` to be active concurrently, respecting max connections / chunk limits.
* To replace a stale mirror without losing progress:
  * The bytes map is file-based, not mirror-specific, so progress is retained when switching mirrors.
  * The existing fallback mechanism already releases the mirror when the active one fails, and the bytes map is reused for the new mirror.

## 6. Key classes / files

* `jd.plugins.DownloadLink` – core link object, `PROPERTY_MIRRORID`, `PROPERTY_CHUNKS`
* `jd.plugins.download.DownloadLinkDownloadable` – runtime downloadable view
* `jd.plugins.download.raf.BytesMappedFileManager` – resume map persistence, `.jdresume` files
* `jd.plugins.download.raf.BytesMappedFile` – in-memory byte map
* `jd.plugins.download.raf.HTTPDownloader` – chunked HTTP downloader
* `org.jdownloader.plugins.MirrorLoading` – conditional skip for mirrors
* `org.jdownloader.controlling.MirrorPackage` – aggregates links by mirror ID
* `org.jdownloader.controlling.DownloadLinkAggregator` – updates mirror packages
* `jd.controlling.downloadcontroller.DownloadWatchDog` – schedules downloads, applies mirror loading

## 7. Recommendations

* For per-block integrity: extend `FileBytesMap` to store checksums per range and integrate with archive verification.
* For multi-mirror: make `MirrorLoading` configurable per file/package, allow multiple active candidates per `MirrorPackage`.
* For stale mirror replacement: current resume map already preserves progress; ensure mirror switch clears the conditional skip promptly.
